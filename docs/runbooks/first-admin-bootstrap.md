# First administrator and invitation setup

This procedure creates the first platform administrator in a new realm. It uses
only the on-site Keycloak service. Run it from a trusted operator workstation,
with shell tracing and terminal session recording disabled. Keep generated
credentials in the approved local secret store and deliver the initial password
to the recipient through that store. Do not paste credentials into commands.

## Prerequisites

- A running Keycloak realm with the `cpi-admin` realm role and registration closed.
- A master-realm administrator credential generated by the operator on site.
- Python 3.11 or later on the workstation; no Python packages are needed.
- For Helm: an existing namespace, Helm, kubectl, a NetworkPolicy-capable CNI,
  and the bootstrap images already loaded in the on-site image store.
- Pause other user and role provisioning while the first administrator is created.
  Run one operator procedure at a time. A disabled client named
  `stoa-first-admin-bootstrap` is reserved for the procedure.
- Leave `stoa.bootstrap.adminServiceAccount.enabled=false` until a human
  administrator has been created. Any existing platform administrator, including
  a service account or a user with an inherited role, prevents bootstrap.

The account receives a generated temporary password and `UPDATE_PASSWORD`.
Enabled default required actions, including `CONFIGURE_TOTP`, are preserved.
The recipient must complete the realm's profile, email and OTP requirements on
first login. Provide on-site mail delivery if email verification is required.

## Prepare the request on site

Use a private operator directory. These environment values identify accounts;
passwords are read without echo or generated locally. Choose the correct master
administrator username for the installation.

```bash
set +x
umask 077
export FIRST_ADMIN_USERNAME=operator
export FIRST_ADMIN_EMAIL=operator@example.com
export KEYCLOAK_ADMIN_USER=admin
python3 - <<'PY'
import getpass
import json
import os
import secrets

request = {
    "username": os.environ["FIRST_ADMIN_USERNAME"],
    "email": os.environ["FIRST_ADMIN_EMAIL"],
    "initial_password": secrets.token_urlsafe(32),
    "bootstrap_id": secrets.token_urlsafe(32),
    "admin_user": os.environ["KEYCLOAK_ADMIN_USER"],
    "admin_password": getpass.getpass("On-site Keycloak admin password: "),
}
fd = os.open("bootstrap.json", os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as stream:
    json.dump(request, stream)
recipient = {key: request[key] for key in ("username", "email", "initial_password")}
fd = os.open("recipient.json", os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
with os.fdopen(fd, "w") as stream:
    json.dump(recipient, stream)
PY
```

Keep `bootstrap.json` in operator-only storage: it also contains the master
administrator password and the request identifier. Never deliver that file to
the recipient. Import only `recipient.json` into the recipient's approved secret
record without printing it. Keep the original operator request unchanged for a
retry, and dispose of both local files after successful delivery.

## Helm

The normal realm bootstrap and first-administrator job are disabled by default.
If the realm does not exist, enable the normal bootstrap with an existing Secret
whose `admin-password` key matches the installed Keycloak administrator. Create
that Secret on site, without a password argument:

```bash
python3 -c 'import getpass, sys; sys.stdout.write(getpass.getpass("Keycloak admin password: "))' |
  kubectl create secret generic realm-bootstrap-auth -n stoa-system \
    --from-file=admin-password=/dev/stdin
```

Create a separate first-administrator Secret from the request on stdin:

```bash
kubectl create secret generic first-admin-input -n stoa-system \
  --from-file=bootstrap.json=/dev/stdin < bootstrap.json
```

Add these non-secret settings to the installation's private values file. Use
on-site domains such as `platform.test` and replace inherited endpoint settings
with addresses for the installation before rendering the chart.

```yaml
stoa:
  domain: platform.test
  bootstrap:
    enabled: true
    keycloak:
      existingSecret: realm-bootstrap-auth
    adminServiceAccount:
      enabled: false
    firstAdmin:
      enabled: true
      existingSecret: first-admin-input
      image: python:3.11.10-alpine
controlPlaneApi:
  signupMode: invite
```

Install or upgrade using the locally available chart and that values file. The
realm bootstrap runs before the first-administrator hook. For an existing realm,
keep `stoa.bootstrap.enabled=false`; firstAdmin can run independently.

```bash
helm upgrade --install installation ./charts/stoa-platform \
  -n stoa-system -f installation-values.yaml
kubectl logs -n stoa-system job/stoa-first-admin
kubectl get job stoa-first-admin -n stoa-system
kubectl delete secret first-admin-input -n stoa-system
```

A successful audit line has reason `created`, a UTC timestamp, realm, account ID
and exit code. Keycloak administration events are enabled without storing event
representations. Verify the account and its effective `cpi-admin` role in the
on-site Keycloak administration console. After delivery, remove the local request
from the workstation using its approved secret disposal procedure. Disable
`firstAdmin.enabled` in the installation values. Remove `realm-bootstrap-auth`
after the realm hook has completed if it has no other consumer.

The Job mounts the request read-only, runs as a non-root user with a read-only
root filesystem, and has no Kubernetes service-account token. Its egress policy
allows only Keycloak in the namespace and DNS in `kube-system`. No RBAC grant is
needed. Adapt existing Keycloak pod labels and service configuration on site if
they differ from the chart's bootstrap conventions.

By default the Job reaches Keycloak over plain HTTP on the namespace service; the
master administrator password and the initial password are therefore protected
only by the cluster network and the egress policy. Set
`stoa.bootstrap.firstAdmin.keycloakUrl` to an `https://` address when Keycloak
exposes a certificate trusted by the Python image's CA store.

## Compose or a host-side command

The default Compose import has no preconfigured human users. Generate the required database,
service and realm client credentials on site and supply the empty variables in
`.env.example` through a private environment file or local secret manager. The
optional federation demo imports also require their own generated inputs. LDAP
seed entries have no password; set individual passwords on site through the
approved directory administration procedure before using those accounts.

After Keycloak is ready, run from the repository root. This command uses the
Keycloak port bound to loopback; it needs no Internet access or additional image.

```bash
KEYCLOAK_URL=http://localhost:8080 \
  bash deploy/docker-compose/scripts/first-admin.sh --input bootstrap.json
```

The file must be owned by the current user, a regular file, and mode 0600.
Alternatively, omit `--input` and redirect the private request on stdin. Never
pass a password or request value as an argument. Verify the role and complete
credential delivery as in the Helm procedure, then dispose of the input file.

## Results and retry

| Exit code | Result | Operator action |
| --- | --- | --- |
| 0 | Administrator created and consumption recorded | Verify, deliver, delete input |
| 10 | Already consumed; no write | Delete input; Helm treats this as success |
| 20 | An administrator already exists; no new account | Use the existing administrator's invitation procedure |
| 21 | Identity conflict or another request is pending | Inspect the on-site realm and original request |
| 22 | Invalid input, file permissions or response | Correct the local configuration |
| 23 | Transport or operation failure | Check local availability; retry the same request |

The realm attribute `stoa.firstAdmin.consumedAt` survives deletion of the created
account. The disabled reservation client binds an interrupted request to its
original identity. A retry can finish an account created before role assignment;
it does not replace that account's password. If interruption occurred after the
role was granted but before consumption was recorded, a retry returns 20. Verify
that account and finish delivery; do not remove the reservation to create another
account. Do not delete or edit the consumption markers during normal operation.

## oauth2-proxy cookie and client secrets

The operator scripts retrieve the client secret from Keycloak and pass it directly
to `scripts/security/store_oidc_secret.py`. The helper sends Secret JSON to kubectl
on stdin and captures command output. It generates a local 32-byte random cookie
key for a new Secret and preserves the existing cookie on subsequent runs.

For manual storage, supply an admin token through a private prompt, select the
client's UUID using the on-site administration console, and use the safe curl
helper. Substitute only non-secret identifiers below.

```bash
set +x
source scripts/lib/secret-input.sh
read -r -s -p 'On-site admin token: ' KC_ADMIN_TOKEN; printf '\n'
export KEYCLOAK_URL=http://localhost:8080
export CLIENT_UUID=selected-client-uuid
curl -sf "$KEYCLOAK_URL/admin/realms/stoa/clients/$CLIENT_UUID/client-secret" \
  -H "Authorization: Bearer $KC_ADMIN_TOKEN" |
  python3 scripts/security/store_oidc_secret.py \
    --client-id observability --cookie --namespace stoa-monitoring
unset KC_ADMIN_TOKEN
kubectl get secret oauth2-proxy-secret -n stoa-monitoring -o name
```

Repeat the retrieval with `--cookie --rotate-cookie` to rotate the cookie key
explicitly. Restart the consuming oauth2-proxy deployments using the site's
rollout procedure; existing sessions will require login again. Do not print or
base64-decode Secret data for verification. To store a client secret in a vault,
use the same retrieval pipeline with `--vault-path secret/oidc --key client-secret`
instead of `--cookie`. Vault authentication must already be configured locally.

## Invitations and offline installation

`SIGNUP_MODE=invite` is the API default. Every trial or standard signup requires
a nonempty code from `SIGNUP_INVITE_CODES`. An empty list accepts no signup.
Distribute high-entropy codes through the approved secret store; the current code
list does not consume them individually. Remove a code from the configured list
when it should stop being accepted. Only explicit `SIGNUP_MODE=open` allows trial
signup without a code; standard signup still requires one. Unknown modes prevent
startup. Invalid and missing invitations have the same response.

Compose exposes both variables. The chart exposes `controlPlaneApi.signupMode`
through `stoa-signup-settings`. The API Deployment is maintained separately from
this chart: reference that ConfigMap using `envFrom`, or its `SIGNUP_MODE` key
using `configMapKeyRef`, and supply `SIGNUP_INVITE_CODES` from an existing Secret.
Restart the API after changing these inputs. Keycloak registration remains closed
in both modes. The default local Google broker is disabled; configure an
approved-user broker flow before enabling a provider that can create accounts.

For isolated installations, preload `python:3.11.10-alpine` and, when the realm
hook is used, `curlimages/curl:8.7.1`, as well as the site's Keycloak and platform
images. Set all deployment endpoints and browser origins to on-site values;
render and inspect the installation's private values before deployment. Neither
first-administrator command downloads code, packages or action links. The Helm
job contacts only the internal Keycloak service and DNS; host-side operations
contact only the operator-selected Keycloak, Kubernetes API or vault.
